# AI development rules — Kalkulátor Bázis 2.1

These rules apply throughout this repository. Follow the user's explicit task scope and the current repository state; do not treat this file as permission to deploy or merge.

## Project and working method

- Maintain the existing **2.1** static-first website; do not start a 3.0 rewrite, replace the stack, or introduce large dependencies unless the task explicitly requires it.
- Work from the current `main` and make changes on a dedicated, narrowly scoped feature branch. Check for related open PRs to avoid conflicting work.
- Use Node.js **>=24.8.0**, `npm ci`, and scripts actually defined in `package.json`. Do not invent commands or report tests as passing unless executed successfully.
- Keep changes minimal, explain their purpose, and avoid unrelated refactors. Keep generated files and their source changes together when required by CI.

## Maintainability and no-layering contract (mandatory)

Read and follow [docs/engineering-development-contract.md](docs/engineering-development-contract.md) before touching runtime code, layout, CSS, calculators, generators, or CI. Its checklist is part of the required PR handoff.

- Before editing, trace the **current canonical implementation**, its callers/loads (including dynamic loads), generator outputs, other open PRs, and regression tests. Prefer modifying the existing owner rather than adding another overlay, `*-fix`, `*-upgrades`, CSS override, or duplicate event handler.
- When replacing functionality, **assess the old implementation for removal**; remove it and its imports/tests/styles when proven unused and safely covered, or document why compatibility is still needed. Never call code dead solely because a static search did not find an import.
- Do not solve a red check by silencing the check or masking an old implementation with another layer. Fix root causes, preserve the static build's source-of-truth and idempotence, and keep cleanup small and reviewable.
- Each relevant PR must say **what was integrated, what was removed, what deliberately remains, and why**; state local test results, CI, merge, and production verification **separately**. No unfounded claims of success.

The 2026-11-08 first-pass audit is [docs/architecture-maintainability-audit-2026-11-08.md](docs/architecture-maintainability-audit-2026-11-08.md). It is a read-only finding list, **not** permission for broad cleanup or an assertion that the site has passed live tests.

## Existing build and validation contracts

- The canonical static build is `npm run static:build` (`scripts/static-build-pipeline.js`). Before making build-related changes, inspect its source, render, and finalize stages. Generated HTML, fingerprints, fragments, and sitemap must stay consistent.
- `index.html` is the canonical, materialized homepage; `fragments/home-redesign-v17-*.inc` are derived using `scripts/sync-home-fragments.js`. Never silently overwrite a hand-edited fragment.
- In the `Site quality` workflow, the asset-fingerprint step runs `node scripts/cache-bust-assets.js`, then checks `git diff --check` and `git diff --exit-code`. When it fails, inspect and commit **only the necessary, reviewed generated changes**; never bypass the check.
- For relevant code changes, run targeted tests and `npm run quality`. For calculations, include `npm run test:math`, `npm run test:invariants`, and affected calculator/model tests. For build changes, include `npm run test:build-pipeline` and relevant static checks. For UI changes, use the existing browser and accessibility checks.
- For docs-only changes, do not regenerate the entire site without cause; GitHub CI remains the final mandatory check.
- For localization, preserve HU/EN/DE semantics, numeric results, input state, metadata and error messages. `docs/localization-progress.md` is generated by `node scripts/localization-inventory.js --write` and should not be manually edited.

## User-facing safety and business requirements

- Never silently change calculator formulas, tax thresholds, default inputs, currency handling, API schemas or the meaning of numerical results. Add reference examples and regression tests for any authorized change.
- Distinguish **enacted regulations**, **official proposals**, and **hypothetical scenarios**, especially for 2027 tax rules. Check authoritative, dated sources before changing legal or financial claims. Keep the 9%/15% tax-rate selection and safeguards intact unless the task explicitly changes them.
- Preserve calculator functionality, SEO/canonical URLs, accessibility, language switching, and approved advertisement placements. Do not increase the site's intended maximum of three authored ad placements per page without explicit approval.
- For news, verify official primary sources, clearly label new versus updated articles, ensure homepage/news-list/sitemap consistency, and never invent publication dates, legal facts, or quotations.
- Do not expose, copy, log, or commit secrets, API keys, production data or sensitive configuration. Use least-privilege credentials and avoid running untrusted PR code with write-capable tokens.

## PR delivery, CI recovery and handoff

1. Understand the request, inspect the relevant code and open PRs, and state the acceptance criteria.
2. Make the smallest safe change on the task branch; add appropriate regression coverage.
3. Run targeted checks. If the static build modifies tracked assets, inspect the diff, retain only intended generated artifacts, and rerun the relevant checks.
4. Open a PR describing: change summary, tests actually run, risks, any manual review needed, and rollback strategy.
5. Check the PR's GitHub Actions results. For failures, read the failing job logs, fix the **root cause on the same branch**, and retry at most three focused cycles. Do not disable tests, edit protected-branch settings or fabricate a green status.
6. If the blocker remains, report its exact step and error with a proposed next action instead of silently stopping.
7. Do **not** merge, deploy to production, or alter branch protections without the user's authorization for that action. A successful CI status alone does not mean production behavior is verified.

When working on multiple tasks, keep news publishing, translations, site redesign and API logic in separate PRs unless an explicit requirement couples them.
